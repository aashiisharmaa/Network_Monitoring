# Backend module structure

Updated: 16 November 2026. Scope: Java source organization, dependency cleanup and
verification. This change does not deploy the running application or complete
outstanding customer alarm business rules.

## Feature ownership

`com.network.monitoring.Application` remains the single Spring Boot entry point.
Its default component/entity/repository scan covers the feature packages below.

| Feature root | Responsibility | Main layers |
| --- | --- | --- |
| `identity` | Authentication, users, companies, sessions and persisted role checks | `api`, `service`, `security`, `entity`, `repository` |
| `licensing` | License issuance, local license verification and request guard | `api`, `service`, `security`, `entity`, `repository` |
| `ingestion` | Uploads, parsing, previews, append/import jobs and identity policy | `api`, `service`, `policy`, `storage`, `entity`, `repository` |
| `kpi` | KPI queries/cache, dashboard, thresholds, validation and derived KPI alarms | `api`, `service`, `dto`, `entity`, `repository` |
| `spatial` | Site analytics, prediction, PCI and load-balancing analysis | `api`, `service`, `entity`, `repository` |
| `rca` | Recommendation jobs, RCA execution, artifact caching and exports | `api`, `service` |
| `reporting` | Daily comparisons, common report composition/rendering, dataset discovery | `api`, `service`, `repository` |
| `reporting.mail` | Common-report delivery profiles and outbox | `api`, `service` |
| `nightly` | Scheduled ingestion/report/delivery coordination and deadline policy | `api`, `service`, `config` |
| `alarm` | Customer native OSS alarm workflow | Existing feature API/DTO/service/repository/ingestion/storage/security/scheduling layers |
| `platform` | Web/security configuration, health, job executors, persistence, Redis and reusable SMTP/capture transport/settings | Infrastructure-specific subpackages |
| `shared` | Common response/errors, JSON codecs and content fingerprints | Small stateless contracts/operations |

120 legacy production classes and 37 existing legacy test classes were relocated.
Tests now live alongside their owning feature packages. Synthetic report fixtures
live under test-only `reporting.support`; a test-only ingestion helper preserves
access to the post-commit hook without widening production visibility.

Exact old-to-new class names are in
[`package-migration.json`](../../backend-java/architecture/package-migration.json).
Java consumers/imports and reflective class names must use the new packages. HTTP
URLs do not depend on those Java package names.

## Responsibility cleanup included

The relocation exposed dependencies that the flat service package hid. These were
resolved by extracting shared operations rather than making all internal helpers public:

- `shared.fingerprint.ContentFingerprint`: bounded streaming SHA-256 and namespaced
  request fingerprints. Reporting/ingestion/KPI/nightly no longer import the internal
  RCA cache-key class. RCA retains ownership of its cache namespace.
- `shared.json.JsonCodec`: general record/date-aware JSON conversion and streaming
  output; its mutable ObjectMapper stays private. External modules no longer access
  `CommonReportModules.JSON` or a renderer's internal map conversion method.
- `shared.json.CanonicalJson`: sorted-map serialization for deterministic identities.
  It intentionally preserves the separate mapper configuration used for hashing.
- `ingestion.policy.ObservationIdentityFields`: canonical identity-field validation
  reused by scheduled and manual ingestion, independent of merge implementation.
- `ReportDatasetController` now delegates to `ReportDatasetService`; tenant scope
  and validation are resolved before `ReportDatasetRepository` executes bounded SQL.
- Generic SMTP/capture transport, settings and address validation belong to
  `platform.mail`, so native alarm delivery and common-report delivery reuse them
  without depending on each other's feature implementation.

Existing fingerprint namespace `rca-cache-v2` is retained for old non-RCA callers
as well, preserving existing persisted key semantics during structural migration.
Any namespace cleanup requires an explicit cache/data-version compatibility decision.
Class-bytecode-based engine fingerprints may naturally change after a package move;
recomputation is preferable to serving artifacts generated by different code.

## Dependency rules

1. Put new code under its business feature; do not recreate root-level `service`,
   `controller`, `entity` or `repository` dumping grounds.
2. API classes own HTTP binding/status; business services own policy/orchestration;
   repositories own persistence queries. Controllers cannot import JDBC/JPA APIs.
3. Repositories cannot import service/API layers. Keep company predicates and
   existing transaction/lock semantics when extracting more SQL.
4. Shared code cannot import business features. Keep it small; business rules do not
   become shared merely because two callers need them.
5. Cross-feature calls use public contracts deliberately. Keep implementation helpers
   package-private; do not widen them solely to satisfy a moved test.
6. Keep Spring configuration in the owning feature or appropriate platform package.
   Keep related Spring Data custom repository interface/implementation together.
7. The application remains one deployable Spring Boot application. Feature packages
   establish ownership; they are not independently deployed or fully isolated modules.

## Compatibility and rollout

- All 186 logical HTTP method/route/parameter contracts remain under a frozen source
  compatibility check. All 304 expanded method/path combinations are documented.
- Entity class simple names, table/column annotations, query semantics, JSON field
  names, bean names and executor qualifiers are preserved. Package changes do not
  require a database schema migration. Existing unapplied feature migrations remain
  a separate deployment responsibility.
- Hibernate metadata validation checks discovery, associations and converters for all
  12 entities without connecting to a database. Spring component registration checks
  detect duplicate bean names and missing feature components.
- `run-backend.ps1` uses a clean build to remove stale classes after package moves.
  Stop the previous development JAR before running that startup script. An isolated
  verification output directory allows builds without stopping the running backend.
- API documentation generation follows the new source locations and keeps the
  existing Word-open handbook intact by writing the updated separate artifact set.

## Verification commands

Run from the repository root:

```powershell
python scripts/verify_backend_api_contract.py
.\scripts\test_alarm_configuration.ps1 -FullSuite -BuildDirectory target/backend-final-verification
python scripts/build_backend_api_documentation.py --output reports/api-reference/structured-backend
```

The isolated MySQL runner does not use the application/customer database. Conditional
KPI/Python/benchmark tests remain skipped when their dedicated fixtures/settings are
absent; those skips must not be described as production acceptance.

Verified result: **152 tests discovered, 121 passed, 31 environment-dependent skips,
zero failures/errors**. This includes the new architecture, entity mapping and stable
cache-key checks plus the existing disposable-MySQL alarm tests. A fresh executable
JAR was built under `target/backend-final-verification`; API documentation coverage
and all 186 source HTTP contracts passed. Entity/table/column/key annotations were
also compared with the pre-migration source for all 12 entities and preserved.

## Remaining design debt

Feature ownership is now established throughout the backend. It does not imply
every service is fully decomposed. Several legacy services still combine substantial
SQL, calculations and orchestration; some controllers still resolve access through
repositories; several domain profiles are nested records in services. Cross-feature
service dependencies remain and are not an enforced acyclic module graph.

Continue extracting focused repositories, immutable request/profile models and
public feature contracts where a specific change requires them. Preserve rollback,
lease, tenant and cache-version guarantees. Measure database/heap/job performance
before adding caches, asynchronous boundaries, brokers or separate services.
Customer BRD pending work remains in [the status review](backend-structure-and-status.md).
